Periodic dependency/spec review per design doc §8.6. Anchored against `package.json` at `7ae146f` (v0.6.1).

The §8.6 risk has materialized: the `2026-07-28` spec revision ("largest since launch") invalidates several of adbmcp's transport-layer design assumptions. The 35-tool surface is unaffected in kind.

## What breaks or changes for adbmcp

1. **`http.ts`'s foundation is now legacy.** The `2026-07-28` spec removes protocol-level sessions and the `Mcp-Session-Id` header; the core is stateless (no `initialize`/`notifications/initialized` handshake; protocol version and client capabilities ride per-request `_meta`; servers MUST implement `server/discover`). adbmcp's stateful per-session transport layer (441-line `src/http.ts`) is 2025-era. Silver lining: cross-call state now officially means "server-minted handles passed as ordinary tool arguments" (SEP-2567) — exactly the pattern adbmcp's `StreamRegistry` already uses for logcat streams. The stream-handle design survives; the HTTP session wrapper does not.
2. **The 35-tool registration surface is mechanical.** v2 renames `.tool()/.prompt()/.resource()` → `registerTool/registerPrompt/registerResource` with explicit config objects; the official codemod (`npx @modelcontextprotocol/codemod@latest v1-to-v2 .`) rewrites imports (package split: `@modelcontextprotocol/core`, `/server`, `/client`, `/node`), symbol renames (`McpError`→`ProtocolError`), handler `extra`→`ctx`, and `package.json`.
3. **The tests' DI seam is the trap.** The migration guide warns the codemod is import-driven: SDK surfaces received as injected parameters fail at **runtime**, not compile time. `test/helpers/fakes.ts` is exactly that seam — manual v1-token grep required.
4. **Auth/guardrails need remounting.** v2's `createMcpHandler` performs no Host/Origin validation — the guide explicitly says DNS-rebinding protection must be mounted in front of it. adbmcp's loopback guard, Host allowlist, and constant-time bearer check survive but relocate. SDK `requireBearerAuth` moved to `@modelcontextprotocol/server`; impact is low since adbmcp hand-rolls its check.
5. **Runtime:** v2 requires Node 20+, ESM-first with CJS builds — adbmcp already complies.

## Spec deltas that reshape the parked v0.7.0 candidates

| Parked candidate | What changed | Consequence |
|---|---|---|
| `screenrecord` (job lifecycle) | Tasks moved out of core into official extension `io.modelcontextprotocol/tasks`: poll-based (`tasks/get`), `tasks/update` for input, servers may return task handles unsolicited | Design space improved — an official long-running-ops shape exists; design against the extension |
| elicitation for `wireless_pair` | Elicitation replaced by Multi Round-Trip Requests (MRTR, SEP-2322): server returns `resultType: "input_required"` with `inputRequests`; client retries the original request with `inputResponses` | Parked mechanism obsolete; pairing-code prompt becomes an MRTR interim result; depends on host MRTR support |
| subscriptions for `adb://devices` | `resources/subscribe`/`unsubscribe` replaced by `subscriptions/listen` (single long-lived POST stream; opt-in types incl. `resourceSubscriptions`) | Viable again under the new mechanism — re-spec before designing |

Other deltas of record: `resultType` required on all results; SSE resumability/`Last-Event-ID` removed; list results carry `ttlMs`/`cacheScope` (`CacheableResult`); deterministic `tools/list` ordering SHOULD; error-code ranges partitioned (`-32020`…`-32099` spec-reserved); Roots/Sampling/Logging deprecated (adbmcp uses none); OAuth DCR deprecated in favor of Client ID Metadata Documents (adbmcp uses plain bearer auth).

## Verdict

**Migrate — deliberately, not urgently.** v1 receives security fixes until ~2027-01-27; v2 is at 2.4.0 and settling; the codemod makes the tool surface cheap. The expensive part is `http.ts`, which carries a real design decision: **clean cut** to stateless (drops 2025-era clients) vs **dual-serve** (legacy session transport + `isLegacyRequest` routing in front of `createMcpHandler` — the documented pattern). Given the installed host base, dual-serve for one release and cut later looks right.

Recommended sequence: (a) update the design doc first — §4.2 deferred list, §5 architecture, and §8.6 risk are factually stale, and the parked candidates' shapes changed; (b) schedule the v2 migration as its own work order (likely two runs: stdio + tools, then the HTTP rewrite), shipping as v0.7.0 with dual-serve.
